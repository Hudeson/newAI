## 本章目标

1. 实现 KGW 绿名单水印的**生成端**与**检测端**，理解为什么检测不需要模型权重；
2. 亲手推导那个 z 检验，并明白 z 的量纲为什么随文本长度增长；
3. 用实验量化三组取舍：强度 δ ↔ 生成质量、鲁棒性 ↔ 改写比例、可行性 ↔ 文本熵；
4. 找到 KGW 一类方法**真实存在的失效边界**——不是实现问题，而是原理限制。

## 原理

### 加水印：把密钥写进采样偏好里

生成第 $t$ 个 token 之前，用前 $h$ 个 token（本章 $h=1$）和密钥算一个哈希种子，
用它把词表 $V$ 伪随机地切成两半：

$$
G_t \subset V,\quad |G_t| = \lfloor \gamma |V| \rfloor \qquad (\text{绿名单})
$$

然后给绿名单里所有 token 的 logit 加一个固定偏置 $\delta$：

$$
\tilde\ell_t[v] = \ell_t[v] + \delta \cdot \mathbb{1}[v \in G_t]
$$

关键点是 $G_t$ **每一步都不一样**（因为种子依赖上一个 token）。
所以生成出来的文本没有任何固定的可疑字符串，人读不出区别，
但整段文本会系统性地偏向「当时那一步的绿名单」。

### 检测：一个单侧二项检验

无水印文本对任何伪随机划分都是无偏的，所以落进绿名单的概率就是 $\gamma$。
数一下长度 $T$ 的文本里有 $|s|_G$ 个绿 token，做正态近似下的单侧 z 检验：

$$
z = \frac{|s|_G - \gamma T}{\sqrt{T\gamma(1-\gamma)}}, \qquad
p = \tfrac{1}{2}\,\mathrm{erfc}\!\left(\frac{z}{\sqrt 2}\right)
$$

两个推论直接决定了这套方法的工程性质：

1. **检测只需要密钥，不需要模型。** 重放哈希就能重建每一步的 $G_t$。
   这是水印能用于「第三方溯源」的根本原因，也是它和「用分类器判断 AI 生成」
   的本质区别；
2. **$z$ 随 $\sqrt T$ 增长。** 证据是累积的，所以短文本天然难判、长文本极易判。
   同时也意味着删掉一部分 token 只会按比例削弱 $z$，不会让水印突然消失。

### 水印藏在哪里？藏在熵里

$\delta$ 只能在「模型本来就犹豫」的位置起作用。如果下一个 token 的概率是
0.999，加 $\delta = 2$ 也翻不动它。形式化地说，单步能注入的偏向量级由分布的
熵决定，**熵为 0 时水印容量为 0**。实验 D 会把这条量出来。

## 代码导读

`dive/watermark.py` 三个部件：

```python
@dataclass
class WatermarkConfig:      # gamma / delta / hash_key / context_width，带参数校验
class GreenListWatermark:   # 既是 logits processor，也是检测器
@dataclass
class DetectionResult:      # z_score / p_value / green_tokens / is_watermarked(threshold)
```

生成端是一个 logits processor，可以直接塞进 `dive.decoding.generate`：

```python
def __call__(self, ids, logits):
    context = list(ids)[-self.config.context_width:]
    biased = np.asarray(logits, dtype=np.float64).copy()
    biased[self.green_ids(context)] += self.config.delta
    return biased
```

检测端就是上面那个公式，逐位置重放绿名单：

```python
for index in range(width, len(tokens)):
    context = tokens[index - width : index]
    if self.green_mask(context)[tokens[index]]:
        green += 1
    scored += 1
z = (green - gamma * scored) / math.sqrt(scored * gamma * (1 - gamma))
```

**一个实现细节值得记住。** `dive.decoding.generate` 的顺序是「先跑 processor，
再做温度缩放」，所以有效偏置其实是 $\delta / T$。想让 $\delta$ 的语义与温度解耦，
就得把水印放到温度之后——这类顺序问题在真实推理框架里同样会咬人。
`dive/watermark.py` 的模块文档里明确写了这一点。

对应测试：`tests/test_watermark.py`（z 值分离、检测器确定性、`WatermarkConfig` 校验）。

## 动手实验

```bash
python3 -m labs.lab05_watermark                  # 全部四个实验，约 90 秒
python3 -m labs.lab05_watermark --delta 4.0      # 换水印强度
python3 -m labs.lab05_watermark --gamma 0.5
```

实验先在槽位语料上训练一个**有真实不确定性**的语言模型（每步平均熵 2.15 nats，
约等于每个位置有 8~9 个合理选项），否则后面几个实验都没意义。

### 实验 A：检测能力（γ=0.25, δ=2.0，各 40 条样本）

| | z 均值 | 极值 | 判定（z≥4.0） |
| --- | --- | --- | --- |
| 带水印文本 | **8.23** | 最小 6.31 | 检出率 **100.0%** |
| 无水印文本 | **1.08** | 最大 2.79 | 误报率 **0.0%** |

两组 z 值**完全不重叠**（6.31 > 2.79），中间还留着很宽的余量。
单条样例：

```
带水印：z=6.306  p=1.433e-10  绿token=37/62 (59.7%)
无水印：z=2.200  p=1.391e-02  绿token=23/62 (37.1%)
```

注意无水印文本的绿 token 比例 37.1% 也高于 γ=25%——单条样本的波动是正常的，
这正是为什么要用 z 检验而不是拿比例直接比阈值。

### 实验 B：δ 的取舍

| δ | z 均值 | 检出率 | 困惑度 | 相对无水印 |
| --- | --- | --- | --- | --- |
| 0.5 | 2.49 | 5% | 8.25 | 0.98x |
| 1.0 | 4.19 | 50% | 8.28 | 0.98x |
| **2.0** | 8.14 | **100%** | 8.25 | **0.98x** |
| 4.0 | 12.27 | 100% | 8.43 | 1.00x |
| 8.0 | 13.49 | 100% | 10.09 | 1.20x |

无水印基线困惑度 8.43。读法：**检出率在 δ=2 就饱和了，而质量代价此时还看不出来**
（0.98x，甚至略低于基线，属于噪声范围）。继续加大 δ 只是在白白牺牲分布保真度——
δ=8 时困惑度涨了 20%。这就是 KGW 论文里 δ 取 2 附近的经验来源。

### 实验 C：鲁棒性——攻击者随机替换 token

| 替换比例 | z 均值 | 仍可检出 |
| --- | --- | --- |
| 0% | 9.53 | 是 |
| 10% | 7.83 | 是 |
| 20% | 6.54 | 是 |
| 30% | 5.37 | 是 |
| 50% | 2.61 | **否** |

z 值随替换比例**平滑下降**而不是断崖式失效。这是统计式水印相对「藏一个特定
字符串」的本质优势：证据分布在整段文本上，攻击者必须改动足够大的比例才能
把 z 压到阈值以下，而那时文本语义也已经被破坏了。

一个诚实的补充：这里的攻击是**随机替换**。真实的改写攻击（用另一个模型
paraphrase）效率更高，因为它会同时改掉大量 token 且保持语义——KGW 论文与
后续工作都承认改写攻击是这类方法的主要威胁。

### 实验 D：没有熵就没有水印

重新训练几个语料熵不同的模型（限制每个槽位的可选词数），其余设置完全一致：

| 每槽可选词数 | 平均熵 | z 均值 | 检出率 |
| --- | --- | --- | --- |
| 1 | **0.01** | 0.56 | **0%** |
| 2 | 0.70 | 5.69 | 100% |
| 4 | 1.39 | 6.48 | 100% |
| 全部 (8~10) | 2.12 | 7.98 | 100% |

这是本章最重要的一张表。熵趋近 0 时模型「只能说那一句话」，
$\delta$ 的偏置推不动它，水印**根本打不上去**——不是打得弱，是打不上。

直接推论：**确定性强的内容天然无法加水印**。代码、公式、事实问答的短答案、
翻译中的专有名词，这些位置的分布本来就是尖峰。这不是 KGW 实现得不好，
而是「把水印藏在采样自由度里」这个思路的适用边界。

## 思考题

1. 从 $z = (|s|_G - \gamma T)/\sqrt{T\gamma(1-\gamma)}$ 出发：若要在 $z \ge 4$
   的阈值下检出，绿 token 比例为 0.4、γ=0.25，最少需要多少个 token？
   这个数字对「检测一条推文」意味着什么？
2. γ 调小（比如 0.1）会怎样？z 的分母变小了，是不是更容易检出？
   同时生成端受到的约束变强了——这两个方向哪个占主导？跑 `--gamma 0.1` 验证。
3. `context_width` 从 1 增加到 4，对**改写攻击**的鲁棒性是变好还是变差？
   （提示：改一个 token 会影响后面几步的绿名单划分？）
4. 实验 D 说明低熵位置打不上水印。能否设计一个方案，把水印只打在高熵位置、
   低熵位置放过？这样做会带来什么新的检测端问题？
5. 假设攻击者拿到了模型但没有密钥，他能通过大量采样统计出绿名单吗？
   需要多少样本？如果密钥定期轮换呢？
6. 水印（本章）与隐写（第 7 章）用的是同一个「采样自由度」资源。
   为什么水印能容忍 30% 的 token 被改，隐写改 1 个就全毁？

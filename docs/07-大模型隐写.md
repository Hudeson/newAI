## 本章目标

1. 实现基于 Huffman 编码的可逆隐写，做到端到端**无损**还原；
2. 从信息论角度理解嵌入率的上限，并用实验验证它就是**模型的单步熵**；
3. 发现一个反直觉的结论：隐写的破绽不是「用词奇怪」，而是「统计特征对不上」，
   而且**过于流畅**同样是破绽；
4. 对比第 5 章的水印，理解「鲁棒统计证据」与「精确逐比特还原」是两个互斥的目标。

## 原理

### 隐写与水印的目标正好相反

| | 水印（第 5 章） | 隐写（本章） |
| --- | --- | --- |
| 目标 | 让持密钥者**能**检测 | 让任何人**看不出**藏了东西 |
| 载荷 | 1 bit（是/不是） | 任意长比特流 |
| 要求 | 鲁棒 | 精确可逆 |
| 改 1 个 token | z 略降，仍可检出 | **全毁** |

两者却在争夺同一个资源：**模型的采样自由度（熵）**。

### 用 Huffman 树把比特流编码成 token 序列

每生成一个 token 时：

1. 取模型概率最高的 $k$ 个候选 $\{v_1,\dots,v_k\}$ 及其概率 $\{p_1,\dots,p_k\}$；
2. 按概率给它们建一棵 Huffman 树，得到前缀码 $C: v_i \mapsto \{0,1\}^{\ell_i}$；
3. 用待隐藏比特流的当前前缀在树上下降，走到哪个叶子就**输出那个 token**，
   并消耗掉 $\ell_i$ 个比特。

Huffman 的性质保证了高概率候选编码更短，所以输出序列在模型看来仍然是
「大概率的续写」，文本读起来自然。平均每 token 携带的比特数满足

$$
H(p) \le \bar\ell < H(p) + 1
$$

其中 $H(p)$ 是候选分布的熵。**这就是嵌入率的理论上限**，实验 B 会量出来。

### 解码：靠共享的模型与前缀重建同一棵树

接收方拥有同一个模型和同一段前缀，于是能在每一步重建出**完全相同**的
候选集与 Huffman 树，再从观察到的 token 反查它的编码：

$$
\text{bits} = C(v_{t_1}) \,\|\, C(v_{t_2}) \,\|\, \cdots
$$

这里有一个必须做对的工程细节：**编解码两端的候选排序必须逐位一致**。
`dive/stega.py` 用 `(-prob, token_id)` 排序，并在建树时用 `(权重, 入队序号)`
打破平局，从而让 Huffman 树的构造完全确定：

```python
order = sorted(top.tolist(), key=lambda t: (-probs[t], t))
...
heapq.heappush(heap, (float(prob), counter, int(token)))   # counter 打破平局
```

只要这个顺序有一点分歧，整条比特流就错位——而且**错得毫无征兆**。

## 代码导读

`dive/stega.py`：

```python
def bytes_to_bits(data) -> list[int]        # 高位在前
def bits_to_bytes(bits) -> bytes
def build_huffman_codes(tokens, probs) -> dict[int, str]   # 确定性构造
@dataclass
class StegoPayload:                          # token_ids / n_bits / steps
    bits_per_token                           # = n_bits / steps
class HuffmanStego:
    def encode(prompt_ids, message, max_tokens) -> StegoPayload
    def decode(prompt_ids, payload) -> bytes
```

`encode` 的主循环就是「建树 → 匹配前缀 → 输出 token」：

```python
while cursor < total_bits and len(produced) < max_tokens:
    tokens, probs = self._candidates(context)
    codes = build_huffman_codes(tokens, probs)
    chosen = _match_code(codes, bits[cursor:])
    cursor += len(codes[chosen])
    produced.append(chosen)
    context.append(chosen)
```

两个边界情形被显式处理了：

- **剩余比特比码字还短**：`_match_code` 补零后再匹配，保证一定能选出一个叶子；
  解码时按 `payload.n_bits` 截断，所以补的零不会污染消息；
- **`top_k = 1`**：`build_huffman_codes` 返回空码 `{token: ""}`，
  嵌入率为 0——这时循环会打不满 `max_tokens` 而抛出明确的错误，
  而不是静默死循环。

对应测试：`tests/test_stega.py`（多组消息与 top_k 的往返一致性、
`build_huffman_codes` 的前缀无关性与确定性）。

## 动手实验

```bash
python3 -m labs.lab07_stega          # 三个实验，约 19 秒
```

载体模型：在槽位语料上训练的 TinyLM，词表 64，训练后困惑度 8.17。

### 实验 A：端到端收发

| | |
| --- | --- |
| 秘密消息 | `密钥7788` |
| 消息比特数 | 80 bit（10 字节） |
| 载体 token 数 | 27 |
| 嵌入率 | **2.96 bit/token** |
| 还原结果 | `密钥7788` |
| 是否完全一致 | **是** |

隐写文本：

```
今天研究员在食堂部署更强检索引擎，需要复测。月初团队在机房压缩更好翻译系统，
指标持平。上周作者在工位调试更强问答系统，效...
```

这段文本读起来和正常生成没有区别，但它的**每一个用词选择都在传递比特**。
只有持有同一个模型和同一段前缀的接收方能把它们读出来。

### 实验 B：容量与隐蔽性的权衡

正常采样的困惑度 8.53 ± 0.49；模型每步熵 **3.12 bit** —— 这是嵌入率的理论上限。

| top_k | bit/token | 载体长度 | 困惑度 | 偏离正常 |
| --- | --- | --- | --- | --- |
| 2 | 1.00 | 80 | **6.77** | **3.6σ** |
| 4 | 2.00 | 40 | 7.39 | 2.3σ |
| **8** | **2.96** | 27 | 8.48 | **0.1σ** |
| 16 | 3.20 | 25 | 10.65 | 4.3σ |
| 32 | 3.08 | 26 | 8.33 | 0.4σ |

两条规律：

1. **嵌入率随 top_k 上升后停在 3.12 bit 附近，正好是模型的熵。**
   Huffman 编码已经逼近信息论上限，再放大候选集也榨不出更多比特
   （top_k=16 的 3.20 略高于 3.12，是有限样本的波动）；
2. **top_k 小的时候文本反而「过于流畅」。** top_k=2 的困惑度 6.77
   显著**低于**正常采样的 8.53，偏离 3.6σ。

第 2 点是本章最反直觉的发现。直觉上「隐写被抓」是因为文本读起来奇怪，
但这里恰恰相反：把候选集压小相当于强制模型只走最高概率的路，
生成的文本比正常采样更「保守」。**隐写分析（steganalysis）分类器抓的是
统计特征的偏离，而偏离是双向的**——太不流畅和太流畅一样可疑。

所以隐写的最优工作点不是「候选集越小越隐蔽」，而是让统计特征贴住正常分布，
本实验里是 top_k=8（0.1σ）。

### 实验 C：脆弱性——改一个 token 会怎样

| 被篡改的 token 数 | 还原是否正确 | 正确字节比例 |
| --- | --- | --- |
| 0 | 是 | **100%** |
| 1 | 否 | **0%** |
| 2 | 否 | 0% |
| 5 | 否 | 0% |

只要改动一个 token，后续所有步骤的上下文就与编码端不同，
Huffman 树随之错位，比特流**完全崩塌**——不是坏掉一部分，是 0%。

对比第 5 章：水印替换 30% 的 token 仍可检出，隐写改 1 个就全毁。
**这不是实现缺陷，而是两者目标不同**：水印要的是鲁棒的统计证据，
所以证据可以冗余地分布在整段文本上；隐写要的是精确的逐比特还原，
每个 token 都承载不可替代的信息，天然不能容错——除非再叠一层纠错码，
而纠错码会消耗容量。

## 思考题

1. 实验 B 里嵌入率停在 3.12 bit。如果换一个熵更高的模型（比如温度调到 1.5），
   嵌入率能突破吗？文本的隐蔽性会怎样？动手改 `--temperature` 验证。
2. 给隐写加上纠错码（比如 Reed-Solomon）可以容忍 $t$ 个 token 被改。
   代价是嵌入率降低多少？在什么攻击强度下这个交换是划算的？
3. `_match_code` 在比特不足时补零。为什么这不会导致解码歧义？
   （提示：`payload.n_bits` 起了什么作用？如果接收方不知道 `n_bits` 会怎样？）
4. 设计一个隐写分析检测器：给你大量正常生成文本和隐写文本，
   你会用什么特征？实验 B 的哪一列告诉你这个特征是可行的？
5. 如果编解码双方的模型版本不一致（比如服务端做了量化），会发生什么？
   这对隐写的实际部署意味着什么？
6. 水印和隐写能同时用吗？把两者叠在同一段文本上，各自的性能会怎样降级？

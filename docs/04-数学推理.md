## 本章目标

1. 把第 2 章的思维链结论推到一个**足够难**的任务上，看清收益的真实量级；
2. 把「思考长度」变成一个可控变量，测出准确率与它的关系；
3. 复现推理蒸馏（STaR / distillation）的**数据效率曲线**，理解相变的位置；
4. 做逐位误差分析，验证模型学到的到底是算法还是查表。

## 原理

### 为什么加法是一个好的探针

三位数加法有三个很难得的性质：

1. **答案唯一且可自动判定**，不需要人评；
2. **正确算法是已知的**（逐位加 + 进位传播），所以可以检查模型学到的
   是不是这个算法，而不只是「答对了」；
3. **难度可精确调节**：位数决定了必须串行执行多少步。

第 $i$ 位的正确输出依赖于第 $i-1$ 位的进位，进位又依赖于第 $i-2$ 位……
这条链是**严格串行**的，长度等于位数。这意味着单次前向想算对，
就必须在固定的层数里塞进 $d$ 步串行计算。

### 三种输出格式，同一批信息

```
直接作答     839+287=1126                                    目标长度  4
倒序草稿     839+287=[6211]1126                              目标长度 10
逐位思维链   839+287=[9+7=6c1;3+8+1=2c1;8+2+1=1c1]1126        目标长度 33
```

三种格式承载的**信息完全相同**，唯一的区别是模型被允许用多少 token 来算。
这是本章实验设计的核心：把「思考长度」隔离成唯一的自变量。

- 「倒序草稿」把结果按低位到高位写出（`6211` 即 `1126` 的倒序）。
  这源于一个真实观察：加法的自然计算顺序是**从低位开始**，
  而标准写法要求先输出高位——模型被迫先给出依赖最长进位链的那一位。
  倒序把这个矛盾解开了；
- 「逐位思维链」进一步把每一位的加法和进位都显式写出（`c1` 表示进位 1）。

### 蒸馏的数据效率

推理蒸馏的做法是：让一个强模型（教师）写出推理过程，用这些轨迹微调小模型。
成本几乎全在「教师肯写多少条」上，所以关键问题是

$$
\text{准确率} = f(\text{教师轨迹条数})
$$

这条曲线的形状决定了蒸馏是否划算。实验 B 会把它测出来，
结果比「单调上升」有意思得多。

## 代码导读

本章的模型与训练完全复用第 1 章的栈，新东西只在任务构造上。
`labs/_tasks.py` 的 `ArithmeticTask`：

```python
@dataclass
class ArithmeticTask:
    digits: int = 2                 # 位数，本章用 3
    style: str = "direct"           # direct / reverse / cot
    n_train: int = 800
    n_test: int = 100
    def prompt(self, a, b) -> str   # "839+287="
    def target(self, a, b) -> str   # 按 style 生成目标序列
    def answer_matches(self, prediction, gold) -> bool
    def to_sft_task(self) -> SFTTask
```

三点实现上的讲究：

1. **零填充对齐**。所有数字都补到固定位数（`839+287=1126`，答案补成 4 位），
   这样每个字符位置的语义是固定的。不补零的话模型还得额外学会处理可变长度，
   会污染实验；
2. **训练集与测试集严格不重叠**。`ArithmeticTask` 在构造时先生成全部
   可能的 $(a,b)$ 组合再切分，测试题**从未在训练中出现**。
   `tests/test_labs.py::test_arithmetic_splits_do_not_overlap` 固定了这条——
   这类实验里最容易犯也最致命的错误就是数据泄漏；
3. **答案判定只看最终数字**。`answer_matches` 从输出里取最后 $d+1$ 个字符，
   所以草稿写错但结果碰对了也算对。这让指标偏乐观，但它衡量的正是
   「作为一个加法器好不好用」。

SFT 的提示掩码（`dive/training.py::sft_batch`）在这里格外重要：
`839+287=` 这部分不参与损失，否则模型会把大量容量花在拟合题目分布上。

## 动手实验

```bash
python3 -m labs.lab04_math_reasoning              # 完整版，约 8 分钟
python3 -m labs.lab04_math_reasoning --quick      # 两位数 + 更少轮数，约 1 分钟
python3 -m labs.lab04_math_reasoning --digits 4   # 更难
```

**这是本仓库最慢的实验**（实测 8 分 21 秒），因为思维链格式的目标序列长达
33 个字符，且要训练三个模型 + 四个蒸馏规模。如果只想看结论走 `--quick`。

### 实验 A：思考长度 vs 准确率（1200 训练题 / 80 测试题，20 epoch）

| 输出格式 | 目标长度 | 最终训练 loss | 训练用时 | 测试准确率 |
| --- | --- | --- | --- | --- |
| 直接作答 | 4 | 0.9856 (ppl 2.68) | 37.4s | **0.0%** |
| 倒序草稿 | 10 | 0.3873 (ppl 1.47) | 56.8s | **1.2%** |
| 逐位思维链 | 33 | **0.0090 (ppl 1.01)** | 131.5s | **92.5%** |

这张表是全仓库对比最强烈的一组数字：**0% → 1.2% → 92.5%**。

三个模型**结构完全相同、题目完全相同、训练轮数完全相同**。
唯一的差别是允许写多少 token。多出来的 token 就是模型多拿到的**串行计算步数**。

几个值得注意的地方：

- **直接作答是彻底的 0%**，不是「差一点」。80 道题一道没对。
  训练 loss 停在 0.99（ppl 2.68）说明模型压根没学会这个映射，
  它只学到了输出的边缘分布；
- **倒序草稿只救回 1.2%**。它把计算顺序理顺了（loss 从 0.99 降到 0.39），
  但**没有增加中间步骤**——每一位的加法和进位仍然要在单次前向里完成。
  这个对照组很关键：它证明收益来自「显式的中间计算」，
  而不仅仅是「输出更长」或「顺序更顺」；
- **代价在时间那一列**：131.5s vs 37.4s，3.5 倍。推理时同样要付这个代价。

对照第 2 章的两位数加法（62% → 72%，+10%），这里是 0% → 92.5%（+92.5%）。
**思维链的收益随任务的串行深度急剧放大**——这解释了为什么它在 GSM8K
这类多步问题上是决定性的，而在单步事实问答上几乎无用。

### 实验 B：蒸馏的数据效率（思维链格式）

| 教师轨迹条数 | 测试准确率 |
| --- | --- |
| 150 | **0.0%** |
| 300 | **1.2%** |
| 600 | **65.0%** |
| 1200 | **91.2%** |

这条曲线不是平滑上升的，它有一个明显的**相变**：300 → 600 之间准确率从
1.2% 跳到 65.0%。

读法：数据量不足时，模型只能记住见过的题目，泛化为 0；
一旦数据量跨过某个门槛，「逐位加 + 进位」这个算法就比死记硬背更**省参数**，
优化过程于是转向学习算法本身，泛化能力突然出现。

工程含义：**蒸馏数据量的收益是非线性的，在相变点之前投入是几乎白费的。**
如果你花钱让教师模型生成了 300 条推理轨迹，看到 1.2% 就放弃，
那你恰好停在了悬崖前面。而 600 → 1200 又开始饱和（65% → 91%），
继续加数据的边际收益在下降。

（注意 1200 条这一行是 91.2%，而实验 A 同样用 1200 条得到 92.5%。
差别来自随机种子与采样顺序，属于噪声量级。）

### 实验 C：错在哪一位？

思维链模型在 80 道测试题里错了 **6** 道。按出错的位置统计：

| 位置 | 出错次数 |
| --- | --- |
| $10^2$ 位 | 4 |
| $10^1$ 位 | 3 |
| $10^0$ 位 | **0** |

典型错例：

```
365+939=[5+9=4c1;6+3+1=9c0;3+9=2c1]1294   （正确答案 1304）
993+257=[3+7=0c1;9+5+1=5c1;9+2+1=1c1]1150   （正确答案 1250）
694+229=[4+9=3c1;9+2+1=1c1;6+2+1=9c0]0913   （正确答案 0923）
```

**个位一次都没错，错误全部集中在高位。** 这是本章最有信息量的观察，
因为它证明模型学到的是**算法而不是查表**：

- 如果是查表，错误会在各位上均匀分布（甚至集中在低位，因为低位组合更多）；
- 而按「逐位加 + 进位」执行时，第 $i$ 位的正确性依赖前面 $i-1$ 位的进位全部正确。
  进位链越长，某一环断掉的概率越大——所以错误必然集中在高位。

看第二个错例：`993+257`，模型算 `9+5+1=5c1`（应为 15，即 `5c1`，**这步是对的**），
但最终答案给了 `1150` 而不是 `1250`——它在把草稿汇总成最终数字这一步丢了信息。
第三个错例 `694+229` 草稿三步全对（`3c1`、`1c1`、`9c0` → 923），
最终却输出 `0913`。**错误集中在「草稿 → 最终答案」的搬运环节**，
而不是算术本身。

这与人做竖式算错的地方是一样的：单步都会，串起来会漏。
它也直接指向了两个改进方向——让最终答案直接引用草稿（而非重新生成），
或者加一步自我验证。

## 思考题

1. 实验 A 的倒序草稿只有 1.2%。如果把倒序草稿改成「倒序 + 进位标记」
   （比如 `[6c1,1c1,2c1,1]`），准确率会更接近逐位思维链吗？
   这个实验能分离出「顺序」与「中间步骤」各自的贡献吗？
2. 实验 B 的相变发生在 300~600 之间。如果把位数从 3 降到 2，相变点会左移还是右移？
   跑 `--quick` 对比一下。相变点与什么量有关？
3. 实验 C 显示错误集中在「草稿 → 最终答案」的搬运环节。
   如果把最终答案改成也逐位输出（`...;8+2+1=1c1]` 之后直接是 `1,1,2,6`），
   准确率会怎样？这对应真实系统里的什么技巧？
4. 逐位思维链的目标长度是 33，训练用时是直接作答的 3.5 倍。
   如果按「相同的训练 FLOPs」而不是「相同的 epoch」来公平比较，
   直接作答能训 70 个 epoch。它能追上来吗？为什么？
5. 本章的思维链格式是人工设计的。STaR 的做法是让模型自己生成推理、
   只保留答对的那些用来训练。在这个加法任务上，STaR 的冷启动会成功吗？
   （提示：初始模型的准确率是 0%。）
6. `answer_matches` 只看最终数字，所以「草稿错但答案对」算对。
   如果改成同时要求草稿全对，实验 A 的 92.5% 会变成多少？
   哪个指标更能反映「模型真的会做加法」？
7. 4 位数（`--digits 4`）的思维链准确率会掉到多少？
   按实验 C 的进位链分析，你能不能**预测**这个数？
